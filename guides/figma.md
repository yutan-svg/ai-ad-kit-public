# 設計原稿（Figma）との突き合わせ

デザインの原稿がある案件で、原稿と実装が一致しているかを**数値で**判定する手順です。
原稿が無い案件（`src/scenes.ts` の数値だけで組む場合）は、この手順書は不要です。

---

## 1. 合否は数値でしか決めない

重ね合わせた画像や並べた画像を見て「ほぼ一致」と判断してはいけません。
過去に、目で見て「ほぼ完全一致」と判定した結果、同じ箇所の修正を5回以上繰り返した例があります。自作の比較スクリプト自体にも誤りがあり、二重に外していました。

判定は `scripts/figma_compare.ts` が出す**平均差**と**最大差**で決めます。

```bash
npx tsx scripts/figma_compare.ts --comp ad-9x16 --figma design/scene3.png --frame 120
```

このコマンド1本で、①静止画の書き出し ②見比べ用の画像2枚（横並び・重ね合わせ）③数値の判定、まで通ります。

### 合格の基準

| モード | 使う場面 | 平均差 | 最大差 |
|---|---|---|---|
| `--mode full`（既定） | 原稿の PNG をそのまま全面に表示しているシーン | < 5 | < 30 |
| `--mode decomposed` | PNG の上に Remotion で見出し・帯・フッターを描いているシーン | < 5 | **判定に使わない** |

`decomposed` で最大差を見ないのは、文字のアンチエイリアスで 1px の色反転が必ず起き、最大差 255 が構造的に出るためです。

| 終了コード | 意味 |
|---|---|
| 0 | 合格 |
| 2 | 要理由提示（平均差 5〜10）。「半透明の描画による構造的な差」「文字の描画差の累積」などの理由を示し、レビュー側の許容判断を仰ぐ |
| 1 | 不合格。実装を直してやり直す |

平均差 5〜10 でも、**差の領域が数十 px 以上に広がっている場合は、文字の描画差ではなく配置のずれ**を疑ってください。

### 帯ごとの差も見る

全体の平均では、1文字レベルの文言の違いやフッター1行の違いが埋もれます。
見出し帯・フッター帯の平均差が 12 を超えたら⚠が出ます。⚠が出たら、その帯の文字を**1文字ずつ**目で照合してから合格にしてください。帯の検査だけでも1文字差は確実には弾けません。

### 注意

両方の画像を `removeAlpha()` で 3 チャンネルに揃えてから比較します。
RGBA（4チャンネル）と RGB（3チャンネル）を混ぜて計算すると、実際には無い差が出ます。スクリプトはこれを済ませていますが、自分で比較を書くときは必ず揃えてください。

## 2. フレームの指定

アニメーションの途中を撮ると、必ず差が出ます。**アニメーションが終わったあとの、静止したフレーム**を撮ってください。

```bash
# フレーム番号を直接指定する
npx tsx scripts/figma_compare.ts --comp ad-9x16 --figma design/scene3.png --frame 120

# シーンの尺から「そのシーンの 90% 地点」を計算させる
npx tsx scripts/figma_compare.ts --comp ad-9x16 --figma design/scene3.png \
  --scene 2 --durations 2.8,2.68,2.35 --at 0.9
```

1つのシーンが内部で前半と後半に切り替わる作りなら、前半は `--at 0.3`、後半は `--at 0.95` で2回撮ります。

出現アニメーションがある要素は、静止したフレームに加えて**アニメーションの途中のフレーム**も確かめてください。小さい状態から始まる拡大は、文字が枠に食い込む原因になります。大きい状態から小さくする向きにしてください。

## 3. 原稿の取得（Figma の MCP を使う場合）

### ノード ID を明示して呼ぶ

| 呼び方 | 依頼主が同時に Figma を触ったとき |
|---|---|
| ノード ID を明示（`get_design_context nodeId="363:5"`） | **影響なし** |
| ノード ID を省略（現在の選択を取得） | **影響あり**。取得するデータが変わる可能性がある |

**原則としてノード ID を明示して呼びます。** これで依頼主の並行作業と衝突しません。

ただし最初の構造把握だけは、ノード ID を知らないため、依頼主の選択に依存する瞬間が必ず発生します。その数十秒だけは「これから原稿の構造を把握します。少しのあいだ Figma を触らないでください」と伝えてください。

### やってはいけないこと

- 全シーンを1回のまとめ取得で済ませて、あとは推測で実装する。文字の大きさ・行間・色が実測されず、あとから何十箇所ものずれが見つかります
- 原稿を取得し直さずに、既存の実装も読まずに「左に 20 ずらす」のような目分量の調整を当てる。同じ箇所を何度も往復することになります
- 取得できない値を、近くの値や他のシーンの値から類推する

**1シーンずつ、取得 → 実装 → 数値判定、を最後まで通してから次のシーンに進みます。**

### 原稿が更新されたとき

依頼主が Figma を直したら、**そのシーンのノードを取得し直します。** 前に取得したデータを使い回さないでください。
どのシーンが直ったか分からない場合は、依頼主に聞いてください。全シーンを取得し直すより速く済みます。

## 4. 実装のときに揃えるもの・揃えないもの

| 原稿に合わせる | 参照元と同じに保つ |
|---|---|
| 座標、幅と高さ | アニメーションの遅延・継続フレーム |
| 文字の大きさ・太さ・行間・字間 | 効果音との同期位置 |
| 色、塗り、線、角丸 | 要素の構成 |
| 図の素材 | 動きの大きさ |

比率が変わったからといって動きを縮めたり、原稿に無い要素を新しく足したりはしません。原稿に無い要素を足すと、動きの山と音の位置がずれて効果音だけが浮きます。

---

## 5. 図形・枠のクリアランス

原稿との一致とは別に、図形と文字の間隔も画素で実測します。

- 文字と枠の間は4辺とも 8px 以上
- 画面端との余白は 10px 以上
- 同じ図が 9:16 と 4:5 の両方にあるなら、**両方で**測る（片方だけ直して展開を忘れるのが最も多い事故）

4:5 は内部の縮尺が違うため、9:16 が合格でも 4:5 が合格とは限りません。

---

## 6. 検証エージェントに渡す

数値が出たら、`design-verifier` に渡して独立した目で確かめてもらいます。
報告には、実行したコマンドと**数値をそのまま**書いてください。

```
[pixel diff] 平均差: X.XX / 最大差: YY → 合格/不合格
```

数値を書かずに「一致しました」とだけ報告してはいけません。
