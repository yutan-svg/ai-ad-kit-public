# 品質を担保する仕組み

作ったものを自分で評価すると、思い込みが必ず入ります。ここでは、それを構造的に防ぐ仕組みと、検証エージェントの使い方をまとめます。

---

## 1. なぜ仕組みが要るのか

実行役は「自分が作ったもの」を自分で評価するため、無意識に甘く採点します（「だいたい合っているはず」「直したから良くなったはず」）。
これは人の認知の癖と同じ構造で、独立した目が無ければ検出できません。

実際に繰り返し起きたのは、次のような形です。

- 重ね合わせた画像を見て「ほぼ完全一致」と判定し、同じ箇所の修正を5回以上繰り返した
- 「完全に静止しています」と説明したが、実態は分離されていなかった
- 書き出したあとフレームを抜いただけで「できました」と報告し、実際には原稿とずれていた
- 「共通部分だから1回確認すれば十分」と自分で判断して工程を省き、複数のシーンでずれが出た

共通する原因は1つです。**「実行する自分」と「結果を客観的に評価する自分」を、同じ作業の中では分離できない。**

---

## 2. 3つの層で分ける

| 層 | 誰が | 役割 | いつ |
|---|---|---|---|
| 層1: 実行役 | あなた（メインの作業） | 制作の本作業。作業中はその場で静止画を確かめる | 常時 |
| 層2: 検証エージェント | 独立したサブエージェント | 実行役の自己申告を鵜呑みにせず、**自分で出力を作って**判定する | 実行役が呼ぶ |
| 層3: 機械検査 | `scripts/` のスクリプト | 数値で測れる最低ラインを保証する。忘れていても不合格で止まる | 各節目 |
| 層4: 門（ゲート） | `scripts/approve.py` ほか | 承諾・人物の参照・テイク上限・耳の確認が無ければ、**そもそも実行させない** | 生成と書き出しの直前 |

層2の弱点は「実行役が呼ばない限り動かない」ことです。だから**呼ぶことが決まり**になっています（`RULES.md` 決まり7・31）。
層3の弱点は「複雑な判断ができない」ことです。重なりの有無・デザインの良否は数値では測れません。
層4は、守られなかったことが実際に起きた4つの決まりを、文章から道具の側に移したものです（一覧は `RULES.md` 第1部0節）。

それぞれの穴を埋め合うので、**1つでも省くと穴が開きます。**

---

## 3. 検証エージェントの使い分け

| エージェント | いつ呼ぶか | 渡すもの | 返ってくるもの |
|---|---|---|---|
| `layout-reviewer` | テロップ・図・人物の配置を変えたら**毎回** | コンポジション名と、審査対象のシーン（id とフレーム番号） | シーンごとの合格／不合格＋理由 |
| `design-verifier` | 設計原稿に合わせて実装したら | 変更したシーンと、変更内容 | 数値つきの合格／不合格 |
| `creative-reviewer` | 一式が仕上がったとき | 完成した動画と `knowledge/project.md` | 表現・訴求・必須表記の監査結果 |

呼ぶときは、**自分が出した静止画を渡さない**でください。エージェントに自分でレンダーさせます（各エージェントの手順書にもそう書いてあります）。
実行役の出力を流用すると、「古い静止画を見せる」という事故が起きます。成果物の検証（`verify_render.py`）も、
書き出した mp4 だけを入力にします（制作中のファイルは見ません）。

### 指摘文の原文で確かめる

指摘への対応が終わったら、**依頼主の指摘文の原文**を別のエージェントに渡し、リポジトリ・静止画・音声で1件ずつ解決済みかを判定させます。

要約した台帳ではなく**原文**を渡してください。要約した時点で、実行役の解釈違いが隠れてしまいます。「直したつもり」を検出できるのは、原文との突き合わせだけです。

## 4. 機械検査を省かない

| タイミング | コマンド |
|---|---|
| 書き出し・確認の前（必ず） | `python3 scripts/preflight.py` |
| 数字・固有名詞を含むセリフ | `python3 scripts/ear_check.py <音声> [<音声2>] --id <id>`（対話。記録が無いと preflight が落ちる） |
| 音声を差し替えた／シーンを割った／文言を変えた | `python3 scripts/align_captions.py` |
| 配置を動かした | `python3 scripts/check_overlap.py <コンポジション名> <フレーム…>` |
| 発音を確かめる | `python3 scripts/asr_gate.py <音声>` |
| 生成音声を耳で聴く前 | `python3 scripts/audio_tools.py check <音声> "キーワード"` |
| 書き出した後 | `python3 scripts/verify_render.py <mp4> --frames` |
| 書き出した後 | `python3 scripts/audio_tools.py scan-gates <mp4> <各シーンの尺>` |

**不合格のまま書き出したり報告したりしてはいけません。**

### テロップ幅の検査とフォント

`preflight.py` のテロップ幅の検査は、「1文字の幅 ≒ fontSize × 係数」という見積もりです。係数はフォントで変わります。
既定は Noto Sans JP の 1.02 です。**フォントを変えたら係数も合わせてください。**

1. `src/brand.ts` の `FONT`（と必要なら `FONT_FILE`）を変える
2. `ai-ad.config.json` の `fontFamily` を同じ名前にし、`fontCharWidth` にそのフォントの係数を足す
   （例: `"fontCharWidth": {"Noto Sans JP": 1.02, "Zen Kaku Gothic New": 1.05}`）
3. 係数の求め方: 代表的な1行を `npx remotion still` で出し、実際の描画幅 ÷（文字数 × fontSize）を測る。
   分からなければ 1.02 のまま少し厳しめに見ておき、はみ出しは静止画で確かめる

### 重なりの検査で数値が 0 にならないとき

`check_overlap.py` は、人物のトーキングヘッドで誤検出が出ます。暖色の室内や木製の机は肌の色域に入るため被写体と数えられ、テロップの黒フチも既定の判定範囲の内側に入ります。

数値が 0 にならないときは、`--halo` を外側に広げて測り直してください。それでも残るなら、**「重なっていない」とは報告しない**でください。口元と目にかかっていないことを静止画で別途確かめ、**数値と所見の両方**を報告します。

### 動きの有無は静止画1枚では分からない

写真のズームやアニメーションを変えたときは、**シーンの頭と尾の2フレーム**を出して差を見てください。静止画1枚では「動いているかどうか」を判定できません。知覚できない大きさのズームを設計してしまった例があります。

## 5. やってしまったときの戻り方

| 状況 | すること |
|---|---|
| 「目視で一致」と言ってしまった | 直ちに撤回し、`figma_compare.ts` の数値を出し直して、数値つきで報告し直す |
| 「検証した」と言ったが実際はしていなかった | 直ちに撤回する。言い訳を足さず、検証をやり直して結果を報告する |
| 工程を省いた | 省いた工程を全部やり直す。省いた判断の理由も報告する（同じ判断を繰り返さないため） |
| 同じ指摘が再び来た | 「直したつもり」を疑う。修正が実際に配線・書き出しに入っていたかを**成果物側**で確かめてから原因を報告する |

いずれの場合も、**取り繕わずに事実を先に言ってください。** 事実と違う報告は、1回で信用を失います。

---

## 6. 報告の書き方

| 場面 | 先頭に書くこと |
|---|---|
| 初稿 | **【初稿】** ＋ 気づいている問題の一覧 |
| 指摘への対応 | 対応した件数と、`FIXES.md` の該当行 |
| 検証の結果 | 実行したコマンドと、出た数値そのまま |

「だいたい大丈夫です」「ほぼ一致しました」のような、確かめようのない言い方をしないでください。
依頼主が自分で検証できる形（コマンド・数値・ファイル名）で書きます。

判断がつかないもの、決まりどおりにするとデザインが崩れる例外的な場合は、自分で判断せず**依頼主に相談**してください。
